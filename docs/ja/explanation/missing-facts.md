ファクトとは、Pointsman が判定のために自分で調べるデータです。たとえば、ある場所が浸水想定区域に入るかどうかです。調べるのに失敗することもあります。ケースに位置がない、データのサービスの応答が遅い、読んでいる途中でプルリクエストに新しいコミットが入った、といった場合です。このときファクトは「欠けた」状態になります。

Pointsman は、欠けたファクトを推測で埋めることはしません。推測した値は本物の値と見分けがつかず、ルールはそれを事実として扱ってしまうからです。代わりに、ファクトが欠けていることをルールから見えるようにし、どうするかはプロファイルで決めます。

## 欠けたファクトの表し方

どのファクトにも、型ごとのフィールドのほかに 2 つのフィールドがあります。

- `missing`: ファクトに値がないとき `true` になります。
- `reason`: 欠けた理由です。たとえば `timeout` や `no_location` です。理由の一覧は[ファクトの型](../reference/fact-types.md#欠けた理由)にあります。

## 「偽」ではなく「不明」

欠けたファクトを比べる条件(例: `facts.flood.rank >= 5`)は、真でも偽でもなく「不明」になります。ルールが当てはまるのは条件が真のときだけなので、不明の条件でアクションが決まることはありません。`and` や `or` と組み合わせたときは、次のようになります。

- `false and unknown` は偽です。偽の部分が 1 つあれば足ります。
- `true or unknown` は真です。真の部分が 1 つあれば足ります。
- `not unknown` は不明のままです。

そのため、データがなかったせいでルールがたまたま当てはまる、ということは起きません。

## プロファイルでの扱い方

どうしたいかを、`missing` を確かめるルールで書きます。`missing` は常に値がわかっています。

```yaml
- when: "facts.flood.missing == true"
  action: review
```

`reason` を使うと、調べるのに失敗した場合と、もともと当てはまらない場合を区別できます。たとえば迂回路は道路の区間についてだけ計算でき、1 つの地点については計算できません。

```yaml
- when: "facts.walk.missing == true and facts.walk.reason != 'no_location'"
  action: review
```

誤って通すと困る判定では、欠けたファクトのルールを最初に置きます。そのルールでは、人に回す(`review`)か、あとでもう一度試す(`retry`。例のプロファイルで使っているアクション名)ようにし、通すアクションにはしません。[AI の回答は判定を厳しくする方向にしか使わない理由](stricter-only.md)も参照してください。

すべての型と理由を含む詳細は、[プロファイルの形式](../../profile-format.md#facts)にあります。
